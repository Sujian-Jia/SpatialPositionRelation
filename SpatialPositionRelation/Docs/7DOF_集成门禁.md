# 7DOF 集成门禁勘察

2026-11-26。已读取原生动力学、控制器、CLI、C ABI、现有 Qt/Unity 输入及参考装配。此阶段只写报告与独立验证结果。两个源码工程、7DOF 原工程和 `dist` 均未修改。当时在门禁处等待确认。用户随后确认方案 A。实施结果以[验收矩阵](ACCEPTANCE_MATRIX.md)及[构建与接口](7DOF_构建与接口.md)为准。

## 原生工况与基线

本机 Windows Release 无 `--scenario` 时实测输出 `DONE station`，与 `main.cpp` 的默认值一致。`README_本次最新版_单航天器组合体锁紧.md` 中称默认 `arm` 的段落和源码、可执行程序有出入。`运行_arm.bat` 已显式传入 `--scenario arm`。建议集成入口明确选择 `ArmCapture` 与 `RigidComposite`，保留 CLI 现有默认行为。基线复验命令如下，输出应写到独立证据目录。

```powershell
& 'D:\Project\261121SpatialPositionRelation\7DOF_masscenter_real_constraint\bin\x64\Release\dynamicsModeling.exe' --scenario arm --lock-model composite --dt 0.001 --output-step 0.02 --duration 80 --csv arm.csv --quiet
```

## 坐标与量纲

| 量 | 7DOF 源码约定 | Unity 工程及拟议输入 |
| --- | --- | --- |
| 惯性坐标 | `[X,Y,Z]` 列向量，右手叉积和右手正转。位置 m，线速 m/s，角速度 rad/s，时间 s。源码确认站端口零姿态朝 +X。未找到惯性空间物理「朝上」的定义。 | Unity 当前是 Y-up 左手展示，世界位置 m。拟以模拟器 +X 保持水平对接轴、+Y 对应 Unity +Y、Z 取反。按此显示约定映射 `P(x,y,z)=(x,y,-z)`，待确认；若团队约定 +Z 朝上，可改提案为 `(x,z,y)`。二者均保留惯性 X 轴、保持向量长度。 |
| 本体与姿态 | `rS=q[0..2]`、`rV=q[32..34]` 表示两个独立刚体本体质心。`q[3..6]`、`q[35..38]` 为本体到惯性的归一化 Hamilton `[w,x,y,z]` 四元数。`u[0..2]`、`u[31..33]` 是两平动速度，`u[3..5]`、`u[34..36]` 是两惯性角速度。诊断欧拉为 ZYX 分解，按 `[roll,pitch,yaw]` 输出，单位 rad。 | `Transform` 接收世界位置、`Quaternion(x,y,z,w)`。同一换基应用于本体系和世界系时 `R_U=P R_C P⁻¹`。反射下极向量转为 `Pv`，角速度等轴向量转为 `det(P)Pω`。从旋转矩阵统一构造四元数，避开欧拉角轴序歧义。 |
| 物理端口 | `P_S=rS+RS·(1.25,0,0)`，`P_V=rV+RV·(-1.25,0,0)`。`ref_station_*`、`ref_visitor_*` 是端口惯性系状态。锁紧时先验证几何约束，再发布共点端口参考。端口速度 `v+ω×(R·localPort)`，与各本体质心速度分开。 | Qt 主距离拟显示物理端口欧氏距离 `‖P_V−P_S‖`，另列质心距离与有符号轴向间隙。左手变换不改长度。两根节点分别接收真实本体位姿，本体到可见装配的刚性偏移及端口绑定都归 Adapter。 |
| 轴向间隙 | `axialGap=(RS·[1,0,0])·(P_V−P_S)`。它是站端口法向投影，可为负。原生 arm 初始样本中约 −1.915 m，端口欧氏距离 3.661 m，质心距 3.175 m，工具到抓捕点只有 0.330 m。 | 旧 Qt 手动「对接距离」用于在 Unity 世界 −X 上偏移追踪器根节点，单位 m。旧对接程序另按目标端面 `right/up/forward` 拼接侧向偏移和正向距离，附加 `demoGapM=0.12 m`。拟改显示文案并明确口径，保留 `relativePositionUnity` 作为追踪器根节点减目标根节点的世界米制向量。旧 0.12 m 展示间隙不施加给物理端口。 |
| 七关节 | `q[7..13]`，数组按 J1–J7，单位 rad。数学零位 `q=0`；`arm` 初始实际角为 `[0.10,-0.18,0.24,-0.14,0.15,-0.10,0.08]`。每个关节绕其零位父侧关节帧局部 +Z，右手正转，函数为 `oldR*Rz(q_i)`。各段还有固定旋转，4、5 段含柔性末端平移和姿态。原注释将物理轴标为待校准假设。 | Unity 现用 Prefab 零位 `baseRotation*Quaternion.AngleAxis(angleDeg,Vector3.forward)`。这只确定旧演示沿 Prefab 局部 +Z，未验证能与模型 J1–J7 逐轴对应。Adapter 按已验证绑定把原生角转成度并集中处理零位、轴、符号。`qCapture` 是初姿，不能当零位偏置。 |
| 末端与抓捕点 | `ArmTool()` 返回含柔性项的惯性位置和旋转。`visitorGrapple=(0,0,1) m` 是 visitor 本体偏移。现有 C ABI 仅给工具位置，缺姿态和逐关节帧。 | 拟新增 C ABI 读取原生 `ArmTool` 姿态。如逐节标定使用求解器帧，还需补一组只读帧导出，复用原动力学几何函数。Unity 保留引用的组内网格，按原生帧做视觉绑定。 |

参考装配有重复关节名，场景生成按最长链选择 `关节1坐标→关节2坐标r→关节3坐标r→关节4坐标r→关节5坐标r→关节6坐标→关节7坐标`。Prefab 里 J3 相对 J2 偏移长 `0.130081 m`，原生 `armOffsets[1]` 长约 `0.244950 m`。这个长度差不能由坐标反射或角度改符号解决。现有场景又会把参考装配最长包围盒缩放到 5.5 m 并居中，空间站演示口为 `x≈−0.4751 m`，载人器为 `x≈+0.8685 m`。这些旧展示口既不在物理 `±1.25 m`，法向也与同名原生主体零姿态不同。「机械臂到达点的坐标」是 Prefab 根节点下独立特征，无法用其证明原生末端位姿。建议确认可以校准**装配绑定、端口及关节帧**，保留组内参考网格与原资源 GUID。逐轴正转、末端六自由度、端口残差须用独立扰动样本验证。

## 主体及现有输入冲突

| C++ 主体 | 源码行为 | 方案 A，建议 |
| --- | --- | --- |
| `station` | 安装七自由度机械臂，控制器初段对本体位置定点。抓捕后搬运 `visitor`，锁紧后站控制器控制组合体。 | 映射到 Unity 己方及敏感器所有者。标签使用「己方航天器（机械臂侧）」。 |
| `visitor` | 起始位置自动对准工具，0.060 m/s 向抓捕台主动接近。抓捕后随机械臂搬运，终段原控制器可辅助，锁紧后禁用自己的主控力矩。 | 映射到 Unity 目标，对应 `target`。演示语义为“己方机械臂工作、两器相对接近”，可用随目标观察的机位表示相对运动。原生惯性轨迹与主动控制方保持可辨。 |

原生 CSV 进一步区分了主动接近与端口闭合。首次工具接触之前的 5.10 s 样本，`station` 本体相对起点只移动 **1.129 mm**，`visitor` 移动 **305.812 mm**，工具到抓捕点的距离由 **0.330 m** 降为 **0.0251 m**。此时物理端口仍相距 **3.413 m**。所以抓捕阶段宜并列显示工具—抓捕点距离与两器端口距离，端口距离仍作为主对接距离。该样本也可用来检验展示是否把初段主动方标反。

方案 B 是保持“己方主动接近目标”的严格主体语义，另立原生工况，重新确定控制方、机械臂所属、触发条件和基线。现有 `arm` 中把 `visitor` 改叫「己方」会让机械臂归属落到「目标」。单纯交换标签不足以符合两个同主体动作。现有 Qt 的 `chaser` 既指敏感器所属，也曾指主动移动的一方，若确认 A 则作为兼容的己方角色 ID，UI 明确显示两器角色和主动方。两个旧候选均实例化同一套带臂 Prefab，需确认 visitor 上多出来的参考机械臂是否只隐藏其显示及碰撞，保留原资产资源。

| Qt 现有功能 | 冲突与拟议处理，等待批准 |
| --- | --- |
| 手动距离、欧拉/四元数、旧演示轨迹/间隙 | 直接写入两器位姿，与唯一真值源冲突。七轴滑块按明确授权移除。建议手动距离与两器姿态在本演示改成原生只读，旧字段保留兼容读取但不进入物理状态。删除写死轨迹与间隙。 |

## 拟议嵌入边界与验证门槛

- 独立项目包装层构建 Win64 DLL。现有 `docking_api` 只编译 plant、参数和 `DockingCAPI.cpp`，现有 C API 接收外部控制和接触信号。完整 arm 场景还用到 `main.cpp` 的 arm 初态及循环、`DockingPDController`、`ExternalContactDemo`、`ExternalPlumeDemo` 和 `ExternalSeparationDemo`。建议将 CLI 的默认工况初始化与单步编排最小抽取成 **同一个原生会话入口**，由旧 CLI 和 DLL 共用，旧 C ABI 原样保留。此做法会改动原目录的应用编排，但不改动力学方程。若要求原目录逐字节零改动，只能在目录外新增包装保留这份编排并以同一 CLI 基线逐次对照，长期存在两份编排同步成本。两种方式在确认前均不实施。
- 调度使用 Unity 实际经过时间做累加，传入 C++ 的每步物理步长固定 0.001 s。每 20 步记录一次全量状态，事件在 native 内逐步留存，UI 渲染可插值。原 CLI 的浮点输出边界有 `min(dt, nextOutput−t)`，且释放条件有连续时间比较。后续须比对严格固定步的调度是否改变事件步号和原始状态，发现漂移先报告。暂停、复位和倍速须保留同一积分时序，不能用 CSV 回放代替运算。
- 适配后状态注入现有 `SpatialSimulationBase` 的场景状态应用路径，敏感器计算、遮挡、照度与传输继续使用原模块。绑定通过固定射线和姿态扰动验极性，记录原生输出、应用后的 Unity Transform、对接口约束和 Qt 展示。将 80 s 基线、源与产物哈希、短/全程回归加入正式构建流程，保留现有结果接口和资源绑定。

源码证据位置为 `7DOF_masscenter_real_constraint/main.cpp`（CLI、初态和会话驱动）、`Controller.cpp`（谁主动接近、锁紧和抓捕请求）、`DockingDynamics.cpp` 的 `GeometryAt`、`ArmTool`、`ReadPortReferenceMotion`（几何和参考系）、`Parameters.cpp`（臂各段标定，含柔性模型）、`DockingCAPI.h`（C ABI）、`SpatialPositionRelation/Assets/Scripts/SpatialRuntime.cs` 的 `ApplyState` 和 `ApplyTrajectoryPose`（旧输入链）、`SpatialSceneBuilder.cs`（参考装配和演示端口），以及 `Spatial_Qt/SpatialPositionRelation/mainwindowstate.cpp`（Qt 发出旧输入）。
